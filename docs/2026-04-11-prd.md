# Product requirements: Rulette

2026-04-11

## Position

Rulette is a **stateless, deterministic compiler for AI coding assistant configuration**.

It handles the full surface area of AI tool config: rules, skills, hooks, MCP servers, sub-agents, and permissions.
It occupies the same conceptual space as `protoc`, `pandoc`, or `jq` — a tool that reads structured input, normalizes it into a typed IR, applies transformations, and emits to any target — but for the domain of AI coding assistant configuration.

## Design principles

1. **Unix philosophy**: Read from stdin or files. Write to stdout or files. Compose with pipes. No daemon, no config files, no local state.
2. **Static binary**: Single binary, zero runtime dependencies. Works in Docker scratch images, Bazel sandboxes, air-gapped environments.
3. **Deterministic by default**: Same input always produces same output. No network calls in the default path. Non-deterministic sources (fetching from GitHub, registries) are explicit escape hatches with mandatory integrity verification.
4. **Typed IR**: All entities (rules, skills, hooks, MCP servers, commands, agents, permissions) are parsed into a typed intermediate representation before any transformation or emission. This catches errors early and enables semantic (not string) transformations.
5. **Composable transforms**: Built-in transforms (filter, map, rename, merge) plus the ability to pipe IR through external tools (`jq`, `markdownlint`, custom scripts).
6. **Security-first distribution**: Content-addressed archives. SHA-256 integrity verification. Lockfiles for reproducible builds. No "fetch latest" without an explicit `--allow-mutable` flag.

## What Rulette is not

- Not an IDE plugin. It has no opinion about your editor.
- Not a rule authoring environment. Write rules in your text editor.
- Not a registry. It can fetch from registries, but it is not one.
- Not a runtime. It runs once, produces output, and exits.

## Scopes of operation

Rulette operates at two distinct scopes.
Both use the same commands and pipeline.
The difference is where inputs come from and where outputs go.

### Project scope

Rules live in a project directory and emit to project-local paths.
This is the default and most common use case.

```sh
# Emit to project-local Claude skills
rulette parse ./rules/ | rulette emit --to claude --out .claude/skills/

# Emit to project-local Cursor rules
rulette parse ./rules/ | rulette emit --to cursor-mdc --out .cursor/rules/
```

### User scope

Rules live in user dotfile directories and emit to user-global config paths.
This is for individuals who want consistent personal rules across all projects — the chezmoi / dotfiles use case.

User-scope paths by tool:

| Tool | User-scope config path |
| --- | --- |
| Claude Code | `~/.claude/CLAUDE.md`, `~/.claude/skills/` |
| Cursor | `~/.cursor/rules/` (global rules) |
| Copilot | `~/.config/github-copilot/instructions.md` |
| Codex | `~/.codex/AGENTS.md` |
| Gemini | `~/.gemini/GEMINI.md` |
| Windsurf | `~/.windsurf/windsurfrules` |

The `--scope user` flag resolves output paths to user-global locations:

```sh
# Emit personal rules to all user-global config paths
rulette parse ~/dotfiles/ai-rules/ | rulette emit --to claude --scope user
rulette parse ~/dotfiles/ai-rules/ | rulette emit --to cursor-mdc --scope user
rulette parse ~/dotfiles/ai-rules/ | rulette emit --to codex --scope user
```

This replaces the need for `npx skills add` or `gemini extension install` commands for personal rule management.
Instead of each tool having its own install mechanism, Rulette provides a single pipeline that emits to any tool's user-global directory.

### Chezmoi integration

For users managing dotfiles with chezmoi, Rulette fits into the template pipeline:

```sh
# In chezmoi's run_after script or template
rulette parse {{ .chezmoi.sourceDir }}/ai-rules/ \
  | rulette emit --to claude --scope user
```

Or as a chezmoi `run_after_` script:

```sh
#!/bin/sh
# .chezmoiscripts/run_after_rulette-sync.sh
rulette parse "$HOME/.local/share/chezmoi/ai-rules/" \
  | rulette emit --to claude --scope user
rulette parse "$HOME/.local/share/chezmoi/ai-rules/" \
  | rulette emit --to cursor-mdc --scope user
```

The output is deterministic, so chezmoi's diff detection works correctly — no unnecessary writes.

### Outputs (backends)

All input formats are also valid output targets.
Additionally: JSON IR (for piping to `jq` or other tools), TOML IR, JSON Schema (for the IR itself).

Not every entity kind can emit to every target.
`rulette inspect --target <format>` reports what survives and what gets dropped.

## Architectural Vision and Unix Philosophy

Rulette strictly adheres to the Unix philosophy. It acts as a stateless, thin transformation layer for AI rules and skills, avoiding complex internal execution engines.

### Magic CLI Input Handling

Rulette automatically detects and handles diverse inputs:

- Standard input (`stdin`)
- Individual files
- Local directories (recursively scanning for rules)
- Archives (e.g., `.tar.gz` files containing a workspace of plugins or skills)

The CLI figures out the source structure automatically, meaning users can directly pass archives or directories without manually extracting or iterating over them.

### Flexible Intermediate Representation (IR)

The core of Rulette is its Intermediate Representation (IR). The IR is not tied to any single tool's source format. Instead, it captures the superset of configuration possibilities (like Claude's extension keys, or Gemini's specific schemas) in a structured, typed way.
This IR is designed to be versioned and adaptable, allowing direct transformations into any target representation (Claude, Gemini, Cursor, Codex, etc.). Format-specific metadata is preserved flexibly using extension fields.

### Pipeline-First Transformations

Rather than building a complex internal querying or filtering language, Rulette relies on external transformers via standard pipelines.
Users are encouraged to output the IR as JSON Lines (`ir-jsonl`), use external tools like `jq` to filter out specific skills or modify metadata, and then pipe the transformed IR back into Rulette to generate the final destination format.

### All-or-Nothing Multi-Output

Rulette supports generating multiple outputs from a single invocation using repeated output flags (e.g., `-o claude:path -o ir-jsonl:-`).
This operation is strictly all-or-nothing: Rulette will compute all target transformations first, and if any single transformation fails, the entire execution aborts without writing partial outputs.

## CLI design

### Flat commands

All commands are top-level, like `protoc`, `jq`, `tar`, and `pandoc`.
With 4 commands in v0.1 and ~10 total, grouping adds ceremony without value.
If the command count grows beyond ~12, subcommand groups can be added as a backwards-compatible change (add `rulette rule parse` as an alias for `rulette parse`).

### v0.1 commands

```json
rulette parse [input...]        Parse input into IR
rulette emit [input...]         Emit IR to a target format
rulette convert [input...]      Parse + emit in one step (the 80% case)
rulette inspect [input...]      Pretty-print IR for debugging
rulette schema [format]         Output JSON Schema for the IR or a target format
```

### v0.1.1 commands

```json
rulette transform [input...]    Apply transformations to IR
rulette validate [input...]     Check rules against schema and policy
```

### v0.2 commands

```json
rulette fetch <source>          Fetch rules from a remote source with integrity verification
rulette lock <manifest>         Generate or update a lockfile from a manifest
rulette verify [lockfile]       Verify fetched content against a lockfile
rulette archive <input...>      Bundle rules into a content-addressed tar archive
rulette unarchive <archive>     Extract and verify a content-addressed archive
```

### `rulette convert` — the 80% case

Most users want "convert this Cursor rule to Claude format" without learning the pipe model.
`convert` does `parse + emit` in a single command:

```sh
# These are equivalent:
rulette convert .cursor/rules/typescript.mdc --to claude --out .claude/skills/
rulette parse .cursor/rules/typescript.mdc | rulette emit --to claude --out .claude/skills/
```

**Options:**

```json
--from <format>     Source format (auto-detected if omitted)
--to <format>       Target format (required)
-o, --out <path>    Output path
--scope <scope>     Output scope: project (default) or user
--merge             Merge multiple rules into a single output file
```

Power users still pipe individual commands for transform chains.
`convert` is the on-ramp, not the ceiling.

### Pipeline composition

Every command reads from stdin or files and writes to stdout or files.
The IR is the lingua franca.

```sh
# Parse a Cursor rule, emit as Claude skill
rulette parse .cursor/rules/typescript.mdc | rulette emit --to claude

# Or use convert for the same thing in one step
rulette convert .cursor/rules/typescript.mdc --to claude

# Parse all rules, filter, emit (v0.1.1+)
rulette parse ./rules/ \
  | rulette transform --filter 'always_apply == true' \
  | rulette emit --to cursor-mdc

# Parse, pipe through jq for custom transformation, emit
rulette parse skills/ --to json \
  | jq '.[] | select(.metadata.license == "MIT")' \
  | rulette emit --to codex

# Fetch from a registry with integrity verification (v0.2)
rulette fetch vercel-labs/agent-skills/react-best-practices --lockfile rules.lock

# Generate a lockfile for reproducible builds (v0.2)
rulette lock rulette.toml --output rules.lock

# Full pipeline: fetch, verify, parse, transform, emit for all targets (v0.2)
rulette fetch --lockfile rules.lock \
  | rulette parse \
  | rulette emit --to claude --out .claude/skills/

# User-scope: emit personal rules to all tools (all-or-nothing multi-output)
rulette convert ~/dotfiles/ai-rules/ \
  -o claude:~/.claude/skills/ \
  -o cursor-mdc:~/.cursor/rules/ \
  -o codex:~/.codex/AGENTS.md \
  -o copilot:~/.config/github-copilot/instructions.md \
  -o gemini:~/.gemini/GEMINI.md \
  -o windsurf:~/.windsurf/windsurfrules
```

### Global flags

```json
--to, -t            Output/target format (json, toml, claude, cursor-mdc, codex, windsurf, copilot, gemini)
--from              Input/source format (for parse and convert; auto-detected if omitted)
--out, -o           Output path (stdout if omitted)
--scope             Output scope: project (default) or user (resolves to user-global config paths)
--quiet, -q         Suppress non-error output
--strict            Fail on warnings (including lossy conversion warnings)
--no-color          Disable colored output
--log-level         Log verbosity (error, warn, info, debug, trace)
```

Note: `--format`/`-f` is deliberately avoided because it is ambiguous (input or output?).
`--from` and `--to`/`-t` are unambiguous and consistent across all commands.

### Non-determinism escape hatch

By default, Rulette never touches the network.
Commands that require network access (`fetch`) require explicit invocation.
Even `fetch` defaults to verifying against a lockfile.
To opt into mutable, unverified fetches:

```sh
rulette fetch vercel-labs/agent-skills --allow-mutable --no-verify
```

This is intentionally verbose.
The dangerous path should be harder to type than the safe path.

## Integrity model

### Content addressing

Every rule and archive is identified by its SHA-256 digest.
The lockfile maps human-readable names to digests:

```toml
# rules.lock
[packages]

[packages."vercel-labs/agent-skills/react-best-practices"]
version = "1.2.0"
sha256 = "a3f2b8c9d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b0c1d2e3f4a5b6c7d8e9f0a1"
source = "https://github.com/vercel-labs/agent-skills/archive/refs/tags/v1.2.0.tar.gz"

[packages."internal/security-policy"]
sha256 = "b4c5d6e7f8a9b0c1d2e3f4a5b6c7d8e9f0a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5"
source = "file:///shared/rules/security-policy.tar.gz"
```

### Manifest

The manifest declares what rules a project needs:

```toml
# rulette.toml
[sources]
react-best-practices = { github = "vercel-labs/agent-skills", path = "react-best-practices", tag = "v1.2.0" }
security-policy = { file = "/shared/rules/security-policy.tar.gz" }
internal-conventions = { path = "./rules/conventions/" }

[emit.claude]
out = ".claude/skills/"
filter = "always_apply == true"

[emit.cursor-mdc]
out = ".cursor/rules/"

[emit.codex]
out = "."
merge = true  # Merge all rules into a single AGENTS.md
```

## Declarative transforms

Transforms can be specified inline or as TOML configuration:

```toml
# transforms.toml

[[transform]]
type = "filter"
field = "metadata.license"
match = "MIT|Apache-2.0"

[[transform]]
type = "rename"
from = "metadata.name"
pattern = "^vercel-"
replacement = "v-"

[[transform]]
type = "map"
field = "body"
shell = "markdownlint --fix --stdin"  # Pipe body through external tool

[[transform]]
type = "merge"
strategy = "concatenate"
separator = "\n---\n"

[[transform]]
type = "set"
field = "metadata.metadata.source"
value = "rulette-generated"
```

Usage:

```sh
rulette parse rules/ \
  | rulette transform --config transforms.toml \
  | rulette emit --to claude
```

## Security threat model

### Threats addressed

| Threat | Mitigation |
| --- | --- |
| Tampered rules in transit | SHA-256 verification against lockfile |
| Mutable "latest" refs | Lockfile pins to exact content hash, not version |
| Prompt injection in shared rules | `rulette validate` can scan for injection patterns |
| Supply chain attack on rule repo | Content-addressed storage; verify before parse |
| Non-reproducible builds | Lockfile + deterministic transforms = bit-for-bit reproducibility |
| Exfiltration via rule fetch | No network by default; `fetch` is explicit and auditable |

### Threats not addressed (out of scope)

| Threat | Why |
| --- | --- |
| Malicious rules that pass validation | Rulette validates structure, not semantic intent. Humans review rules. |
| Compromised binary | Use standard binary verification (cosign, SLSA provenance). Separate concern. |
| AI misinterpreting valid rules | The AI runtime's problem, not the compiler's. |

## IR design

### Entity types

AI coding tools define several distinct entity types, not just "rules."
Every tool implements these differently, which is exactly why the IR layer exists — it normalizes the mess.

The Rulette IR is a versioned, tagged union of entity types sharing a common envelope:

```json
RuletteDocument
├── ir_version: String            ("0.1" — semver, for forwards/backwards compat)
├── entities: Vec<RuletteEntity>

RuletteEntity
├── kind: EntityKind          (rule, skill, hook, mcp-server, agent, permissions)
├── source: SourceInfo        (origin file, format, path)
├── metadata: CommonMetadata  (optional: name, description, version, license)
├── activation: Activation    (how/when this entity activates — see below)
├── body: Option<String>      (markdown/text content, when applicable)
├── config: Option<Value>     (structured config, when applicable — JSON-compatible)
└── extra: HashMap<String, Value>   (single map for all extension fields — well-known and unknown)
```

The `extra` map is a single flat namespace.
Well-known keys use the `rulette:` prefix (provisional — may move to a domain-based namespace like `io.rulette.*` before 1.0).
Unknown keys from source formats are preserved as-is for passthrough.
There is no separate `extensions` map — one map avoids the migration problem where a key moves between maps across IR versions.

### Concrete IR examples

A Cursor MDC rule parsed into the IR:

```json
{
  "ir_version": "0.1",
  "entities": [
    {
      "kind": "rule",
      "source": {
        "file": ".cursor/rules/typescript.mdc",
        "format": "cursor-mdc"
      },
      "metadata": {
        "description": "TypeScript conventions for this project"
      },
      "activation": {
        "mode": ["glob"],
        "globs": ["src/**/*.ts", "src/**/*.tsx"]
      },
      "body": "Use strict TypeScript. Prefer `interface` over `type` for object shapes.\nAvoid `any` — use `unknown` and narrow with type guards.\n"
    }
  ]
}
```

A Claude Code skill (slash command + model activated) parsed into the IR:

```json
{
  "ir_version": "0.1",
  "entities": [
    {
      "kind": "skill",
      "source": {
        "file": ".claude/commands/review-pr.md",
        "format": "claude-command"
      },
      "metadata": {
        "name": "review-pr",
        "description": "Review a pull request for correctness, security, and style"
      },
      "activation": {
        "mode": ["manual", "model"],
        "description": "Use when the user asks to review a PR or mentions pull request review"
      },
      "body": "Review the pull request at $ARGUMENTS.\n\nCheck for:\n1. Logic errors and edge cases\n2. Security vulnerabilities\n3. Style consistency\n",
      "extra": {
        "rulette:tool-access": [
          {"tool": "Bash", "pattern": "gh:*", "allow": true},
          {"tool": "Read", "allow": true}
        ]
      }
    }
  ]
}
```

A mixed document with a rule and an MCP server (v0.1.1+):

```json
{
  "ir_version": "0.1",
  "entities": [
    {
      "kind": "rule",
      "source": {"file": "CLAUDE.md", "format": "claude"},
      "metadata": {"description": "Project conventions"},
      "activation": {"mode": ["always"]},
      "body": "Use one sentence per line in documentation.\nPrefer fd over find.\n"
    },
    {
      "kind": "mcp-server",

```

### IR versioning

The IR is versioned with a semver string in every emitted document.
This enables:

- Forward compatibility: older Rulette versions can reject IR they don't understand
- Backwards compatibility: newer Rulette versions can read and upgrade older IR
- Caching and diffing: IR version + content hash = stable cache key

```json
{
  "ir_version": "0.1",
  "entities": [...]
}
```

The IR version is independent of the Rulette binary version.
IR schema changes follow semver: patch for additive fields, minor for new entity kinds, major for breaking envelope changes.

### Activation model

Skills, rules, and commands all have an activation dimension — when and how they become active.
Rather than scattering this across entity kinds, the IR normalizes activation into a shared struct:

```json
Activation
├── mode: ActivationMode      (always, glob, pattern, manual, model)
├── globs: Option<Vec<String>> (file patterns — Cursor's globs, directory scoping)
├── pattern: Option<String>    (content/message pattern matching)
├── description: Option<String> (human-readable trigger description)
```

| Mode | Meaning | Used by |
| --- | --- | --- |
| `always` | Injected into every context | Cursor `alwaysApply: true`, `CLAUDE.md`, `.windsurfrules` |
| `glob` | Active when matching files are open/referenced | Cursor MDC `globs`, Codex directory scoping |
| `pattern` | Active when user message or context matches a pattern | Claude skill triggers |
| `manual` | User explicitly invokes (slash command) | Claude `/skill-name`, Gemini slash commands |
| `model` | The model decides when to activate based on description | Claude skills (model-activated), Agent Skills |

Claude Code skills are the most advanced here — they can be both `manual` (user types `/skill-name`) and `model` (model activates based on the trigger description).
The IR supports multiple activation modes per entity via a list.

### Entity kind taxonomy

| Kind | What it is | Supported in | Examples |
| --- | --- | --- | --- |
| **rule** | Instructions injected into the AI context. Activation: always-on, glob-matched, or directory-scoped. | v0.1 | `CLAUDE.md`, `.cursorrules`, `.cursor/rules/*.mdc`, `AGENTS.md`, `.windsurfrules`, `copilot-instructions.md`, `GEMINI.md` |
| **skill** | Packaged instructions with structured metadata (name, version, license). Activation: manual (slash command), model-activated, or both. Subsumes "commands" — a skill with `activation: [manual]` is a slash command. | v0.1 | Agent Skills `SKILL.md`, Claude Code skills, Claude Code commands, Gemini slash commands, Gemini extensions |
| **hook** | Pre/post actions triggered by tool events (file save, command run, tool call). | v0.2 | Claude Code hooks (`settings.json`), Cursor task runners |
| **mcp-server** | Model Context Protocol server configuration. Connects the AI to external tools/data. | v0.1.1 | Claude Code MCP (`settings.json`), Cursor MCP (`.cursor/mcp.json`), VS Code MCP |
| **agent** | Sub-agent definitions with specialized roles, tools, and instructions. | v0.2 | Claude Code sub-agents, Codex agents, Cursor agent configs |
| **permissions** | Allowed/denied tool and file access patterns. | v0.2 | Claude Code `allowed-tools`, Cursor tool restrictions |

Note: `command` was considered as a separate entity kind but rejected.
Claude Code skills already subsume commands (a skill with `manual` activation is a slash command).
Gemini slash commands are representable as skills with `activation: [manual]` and a `description` + `body` (the prompt).
A separate `command` kind would create ambiguity about whether a parsed Claude `commands/foo.md` is a command or a skill — the answer is always "skill with manual activation."

### How tools map to entity kinds

| Tool | rule | skill (incl. commands) | hook | mcp-server | agent | permissions |
| --- | --- | --- | --- | --- | --- | --- |
| Claude Code | `CLAUDE.md` | skills/, commands/ | settings.json hooks | settings.json mcpServers | sub-agents | settings.json permissions |
| Cursor | `.cursorrules`, `.mdc` | — | — | `.cursor/mcp.json` | — | — |
| Codex | `AGENTS.md` | — | — | — | AGENTS.md (scoped) | — |
| Copilot | `copilot-instructions.md` | — | — | — | — | — |
| Windsurf | `.windsurfrules` | — | — | — | — | — |
| Gemini | `GEMINI.md` | extensions, slash commands | — | — | — | — |
| Agent Skills | — | `SKILL.md` | scripts/ | — | — | allowed-tools |

Dashes mean the tool has no native concept for that entity kind.
When emitting to a tool that doesn't support an entity kind, Rulette either:

1. Drops the entity (with a warning in `--strict` mode)
2. Inlines it into the closest equivalent (e.g., agent → rule with "you are an agent that..." preamble) when a reasonable mapping exists

### Skills vs rules

A skill is a rule with structured metadata.
Parsing `.cursorrules` produces a `rule` entity.
Parsing `SKILL.md` produces a `skill` entity.
Converting rule → skill requires the user to supply missing metadata (via `--name`, `--description` flags) or Rulette generates defaults from the filename and first paragraph.
Converting skill → rule is lossless — drop the extra metadata.

### Agent Skills as the skill baseline

The Agent Skills format (agentskills.io) is the most standardized skill format, adopted by 20+ tools.
Rulette uses Agent Skills field names as the canonical skill metadata: `name`, `description`, `version`, `license`, `compatibility`, `allowed-tools`, `metadata`.
Format-specific fields that don't map to these go into `extra`.

### Lossy by design

Not every entity maps cleanly to every target.
This is inherent — Cursor has no concept of hooks, Copilot has no concept of skills.

**Default behavior**: Rulette emits what it can and prints warnings to stderr for dropped entities and fields.
The output is still valid — lossy conversion is not an error.
This matches `pandoc`'s behavior: it warns but produces output.

**`--strict` mode**: Fails (exit code 3) on any information loss.
Useful in CI to ensure no drift.

**`rulette inspect --target <format>`**: Shows exactly which entities and fields survive, which are dropped, and which are approximated.

### Mixed directory parsing

When `rulette parse` receives a directory, it recursively discovers all recognized files and produces a single `RuletteDocument` with all entities.
A directory containing `CLAUDE.md`, `settings.json`, and `skills/` produces a flat list of rule, mcp-server, and skill entities.

No deduplication is performed in v0.1 — if the same logical rule appears in both `.cursorrules` and `CLAUDE.md`, both are included.
Deduplication is a transform (`rulette transform --dedup`) planned for v0.1.1.

### MCP server normalization

MCP server configs are structurally similar across tools (server name, command/URL, environment, arguments) but stored in different files with different schemas.
The IR normalizes to:

```json
{
  "kind": "mcp-server",
  "metadata": { "name": "filesystem" },
  "config": {
    "command": "npx",
    "args": ["-y", "@modelcontextprotocol/server-filesystem", "/path"],
    "env": {}
  }
}
```

This maps to `settings.json` mcpServers for Claude, `.cursor/mcp.json` for Cursor, etc.

### Hook normalization

Hooks vary the most across tools.
Claude Code hooks have event types (`PreToolUse`, `PostToolUse`, `Notification`, `Stop`, `SubagentStop`), matchers, and shell commands.
Other tools have more limited hook models or none at all.
The IR captures the superset and drops unsupported fields per target.

### Well-known extension keys

The `extra` field carries format-specific semantics that don't map to the common envelope.
To avoid an untyped soup, Rulette defines well-known extension keys with documented schemas.
Unknown keys are preserved as passthrough — the IR never drops data it doesn't understand.

| Key | Type | Used by | Description |
| --- | --- | --- | --- |
| `rulette:activation` | `Activation` | rule, skill, command | Activation conditions (see activation model above) |
| `rulette:tool-access` | `Vec<ToolAccessRule>` | permissions, skill, agent | Granular tool allow/deny with glob patterns. Claude's `Bash(git:*)`, `Read(~/.ssh:deny)`. |
| `rulette:hook-event` | `HookEvent` | hook | Event type (`PreToolUse`, `PostToolUse`, etc.), matcher pattern, shell command |
| `rulette:agent-tools` | `Vec<String>` | agent | Per-agent tool restrictions (scoped allowed-tools) |
| `rulette:models` | `Vec<String>` | skill, agent | Model compatibility list (e.g., `["claude-sonnet-4", "gpt-4o"]`) |
| `rulette:seeded` | `bool` | skill | Whether the skill was seeded/built-in vs user-defined |
| `rulette:directory-scope` | `String` | rule | Codex-style directory scoping (path relative to repo root) |
| `rulette:settings-overrides` | `Value` | permissions | Tool behavior config: model, maxTurns, env, etc. Claude-specific today. |

Well-known keys use the `rulette:` prefix (provisional — may move to a domain-based namespace like `io.rulette.*` before 1.0).
Third parties can define their own keys with their own prefix (e.g., `myorg:compliance-level`).
The schema for each well-known key is published via `rulette schema --extension <key>`.

### Permissions: entity vs metadata

Permissions appear in two places: as a top-level `permissions` entity (from Claude `settings.json` global permissions) and as `rulette:tool-access` on individual skills/agents (per-entity allowed-tools).
These are semantically different:

- **Entity-level permissions** are global tool settings (e.g., "Bash is allowed everywhere in this project")
- **Per-skill permissions** scope tool access to a specific skill (e.g., "this skill can use Bash(git:*) but nothing else")

When emitting to Claude, global permissions go to `settings.json` and per-skill permissions go to the skill's `allowed-tools` frontmatter.
There is no merge ambiguity because they represent different scopes.

### Settings and tool configuration

Tool behavior settings (`model`, `maxTurns`, `env`, `customApiKeyResponses`) are not rules, skills, or permissions — they are runtime tool configuration.
These are captured via `rulette:settings-overrides` in the `extra` map of a `permissions` entity, not as a separate entity kind.
This is a pragmatic choice: Claude `settings.json` mixes permissions and settings in one file, so the parser emits them together.
If other tools develop structured settings files, a dedicated `settings` entity kind may be warranted in a future version.

**Design rationale**: This is the same pattern as OpenTelemetry semantic conventions and OCI annotations — a shared namespace of typed keys over an extensible map.
It avoids bloating the core envelope with fields only one tool uses, while still providing type safety and documentation for the fields that matter.

### Claude Code as the reference implementation

Claude Code has the richest configuration surface of any tool today.
It serves as the high-water mark for IR design — if the IR can round-trip Claude Code config, it can handle anything.

Claude-specific capabilities that the IR must preserve:

| Capability | IR mapping |
| --- | --- |
| Skills as slash commands (`/skill-name`) | skill entity with `activation: [manual, model]` |
| Model-activated skills | skill entity with `activation: [model]` + description-based matching |
| Granular tool permissions (`Bash(git:*)`) | `rulette:tool-access` extension key |
| Hook event taxonomy (PreToolUse, PostToolUse, Notification, Stop, SubagentStop) | `rulette:hook-event` extension key |
| Sub-agent tool restrictions | `rulette:agent-tools` extension key |
| Settings overrides (model, maxTurns, env) | `rulette:settings-overrides` extension key |
| MCP server config with env vars | mcp-server entity with config.env |

When emitting to a less capable tool (e.g., Cursor), the IR preserves these fields but the emitter drops what the target can't represent.
When emitting back to Claude, nothing is lost.

## Versioning and milestones

### v0.1 — core pipeline (minimum viable)

**Commands**: `parse`, `emit`, `convert`, `inspect`, `schema`

**Entity kinds**: rule, skill (the two most common and standardized)

**Targets**: Claude, Cursor MDC, Codex (AGENTS.md), Agent Skills (SKILL.md), JSON IR
**Stretch targets**: Copilot, Windsurf, Gemini (trivial — plain markdown or simple JSON)

**Features**:

- Auto-detection of input format and entity kind
- `--scope user` for user-global config path resolution
- Lossy conversion warnings via `inspect --target` and `--strict`
- rule ↔ skill promotion/demotion with `--name`, `--description` flags

### v0.1.1 — transforms, validation, and MCP

**Commands**: `transform`, `validate`

**Entity kinds**: add mcp-server

**Features**:

- Filter, rename, set, merge, shell pipe transforms
- Deduplication transform (`--dedup`)
- IR schema and optional policy validation
- Declarative transform pipelines via TOML config
- MCP server config normalization (Claude ↔ Cursor ↔ VS Code)

### v0.2 — supply chain and remaining entities

**Commands**: `fetch`, `lock`, `verify`, `archive`, `unarchive`

**Entity kinds**: add hook, agent, permissions

**Features**:

- Lockfile-verified fetching from GitHub, registries, local archives
- `rulette.toml` manifest and `rules.lock` lockfile formats
- Content-addressed tar archives
- Sigstore/cosign signing support (beyond checksums)
- `--allow-mutable` and `--no-verify` escape hatches
- Hook normalization (Claude hooks → closest equivalent per target)
- Sub-agent definitions
- Permission/allowed-tool normalization
- GitHub Actions example workflow

### v0.3 — evaluation (stretch)

- Policy check commands (injection scanning, size limits, forbidden patterns)
- Semantic diff between entity sets
- Coverage reporting (which entity kinds survive per target)

## Positioning and adoption

### Honest v0.1 positioning

v0.1 ships with 2 entity kinds (rule, skill) and 5 targets (Claude, Cursor MDC, Codex, Agent Skills, JSON IR).
Rulesync already supports 28+ targets and 215 releases.
Rulette v0.1 is not a general-purpose replacement for rulesync.

v0.1 targets a specific audience:

- **Bazel / hermetic build users** who cannot run Node.js in their build graph
- **Security-conscious teams** who need a static binary with no runtime dependencies
- **Organizations standardizing on Agent Skills** who need deterministic conversion
- **Developers who think in pipes** and want to compose with `jq`, `markdownlint`, etc.

The general-purpose replacement story comes with v0.2 (supply chain) and the broader entity kind coverage in v0.1.1+.

### What survives if Agent Skills wins

If every tool natively reads `SKILL.md` and the format translation value evaporates, Rulette's surviving value is:

1. **Supply chain integrity** — lockfiles, content-addressed archives, verified fetches
2. **Transform pipelines** — filter, rename, merge, shell pipe, declarative TOML transforms
3. **Multi-entity management** — MCP servers, hooks, permissions, agents (these will not converge to a single format anytime soon)
4. **User-scope management** — chezmoi/dotfiles story for personal configuration
5. **Policy and validation** — organizational rule standards, injection scanning

Format translation is the gateway feature, not the moat.
The moat is determinism and security for the full configuration surface.
