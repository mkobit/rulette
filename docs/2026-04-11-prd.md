# Rulette 0.1 product requirements

## Product statement

Rulette is a static, offline compiler for local AI-agent guidance packages.
It translates documented native layouts through a package-aware compilation graph instead of treating every input as interchangeable prompt text.

## User outcome

A maintainer can inspect native guidance from one supported harness, retain its source provenance and package resources, select exact package identities, and lower the selected graph for another supported harness.
The compiler reports representational loss before publication so a maintainer can review it deliberately.

## Release scope

The v0.1 portability surface contains five harness domains: Codex, Claude, Cursor, OpenCode, and Antigravity.
The v0.1.0 distribution is `rulette-v0.1.0-x86_64-unknown-linux-musl.tar.gz`, a fully static Linux binary with no runtime dependencies.
Users verify the archive against its `.sha256` sidecar before extracting `rulette`.
Each frontend recognizes only layouts the named harness loads.
Each frontend produces a deterministic `CompilationGraph` containing ordered packages and diagnostics.
The native lowering layer produces deterministic artifacts and capability findings without writing a destination.
The publication workflow stages artifacts for review before a separately authorized apply step.

## Compilation model

Rules and skills are the only portable v0.1 semantic units.
A standalone rule file becomes one rule package.
A native skill directory becomes one skill package with one Markdown primary instruction and zero or more opaque resources.
Package identifiers are content-addressed and are not inferred from display names.
Source provenance, normalized package roots, opaque resources, and executable metadata remain attached to retained packages.

Agents, hooks, MCP settings, permissions, plugins, registries, and fetch behavior are outside the narrow v0.1 semantic portability contract.
Agents, hooks, MCP settings, permissions, and other native-only semantics remain opaque unsupported packages with structured diagnostics.
Rulette does not silently convert them into portable rules or skills.
Unrecognized files outside a recognized package are warnings rather than graph resources.

## Explicit snapshot builds

Generated snapshots from Beads, OpenSpec, CI, or another external tool are ordinary explicit source inputs.
The producer runs outside Rulette, and Rulette never executes, discovers, or synchronizes with that producer.
Each invocation selects one homogeneous native frontend with explicit `--from <frontend>` or unambiguous `--from auto`.
Graph JSON and graph TOML are explicit interchange readers only, and native, JSON, and TOML inputs cannot be mixed.
At most one standard-input stream is accepted, and it must be an explicitly selected tar, gzip-compressed tar, graph JSON, or graph TOML source.
Plain native standard input is rejected because it has no naming and layout contract.
One shared ledger enforces the 10,000-observation, 32 MiB per-resource, and 256 MiB total invocation limits across every explicit input and the permitted standard-input stream.
All candidates are aggregated and collision-checked before capability analysis, lowering, staging, or publication.
Collision diagnostics show unchanged package provenance together with transient outer input identity, while capability and lowering findings show package provenance only.
Targets normalize and deduplicate to one or more unique resolved targets, and check, stage, and apply remain a one-way source-to-derived-artifact lifecycle.
Staged and published artifacts are derived outputs and are never imported, merged, or synchronized into a later build.

## Safety and determinism

The compiler accepts explicitly supplied local files, directories, safe tar inputs, and one permitted standard-input stream.
It also re-ingests explicitly selected graph JSON or TOML documents when their graph version and every graph invariant validate.
It does not fetch sources, load plugins, execute downloaded code, auto-discover configuration, or retain local state.
Inputs, graph ordering, selection, lowering, and staged plans are deterministic for the same supplied bytes and options.
Unsafe paths, malformed packages, identity collisions, and unauthorized publication are hard errors.

## Selection and loss policy

Selection uses exact package identifiers only.
No selector retains every package in stable package-identifier order.
Repeated selectors form one deterministic union.
Selection never edits instruction text, metadata, activation, resources, package roots, or frontend payloads.

Lossy or dropped lowering outcomes are strict by default and fail before staging.
`--allow-lossy` is an explicit acceptance decision for reviewed loss findings and may permit staging while preserving every finding in the result and staged plan.

## Non-goals

Rulette is not an agent runtime, prompt marketplace, package registry, network fetcher, plugin host, or local-state manager.
It does not define portable agents, hooks, MCP servers, permissions, text rewriting, or metadata mutation in v0.1.
It has no registry or fetch subsystem and does not write native artifacts directly to arbitrary destination paths.

## Native migration and publication

Direct native output paths are retired in favor of a stage, review, and apply workflow.
`--stage` writes a deterministic plan and artifacts without publishing a live destination.
`--apply` is the only publishing operation and requires the expected plan digest and explicit root authorization such as `--allow-project-root`.

## Release criteria

The public library exposes graph validation, exact package selection, capability analysis, lowering plans, and staged-publication primitives without exposing the retired flat document model.
The command layer remains a thin adapter over those library contracts.
Focused fixtures prove every core frontend retains package boundaries, provenance, primary instructions, opaque resources, and unsupported semantics.
Release validation proves a static binary has no runtime network, dynamic loading, configuration discovery, or state-store dependency.
